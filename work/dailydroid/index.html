What DailyDroid tests

We selected five apps in each of five categories and wrote a simple, medium and hard task for each app. The resulting 75 tasks cover everyday interactions with forms, search, media controls and system settings.

Two views of the same screen

We extended AutoTask to capture a screenshot at each step. The text-only setting used the Android UI tree converted to simplified HTML. The multimodal setting added a screenshot from the same step. Both models ran all 75 tasks in both settings, with the same emulator configuration and a ten-step cap. We reviewed the logs to verify each outcome.

Where the runs broke down

The Failure Handbook distinguishes system-level blockers from errors the agent makes while it can still act. Failure to retrieve the UI was the most frequent system-level issue, affecting 23–25 of the 75 trials in each condition.

Selected categories from Table 3, the Failure Handbook
FailureWhat happens
UI retrievalThe system fails to fetch the app’s interface.
UI parsingThe interface is retrieved, but the system cannot identify the controls needed to continue.
ExecutionThe intended action is identified but cannot be performed.
Model prediction or reflectionThe agent picks the wrong action or misjudges whether a step worked.
Step limitThe run exhausts its action budget, sometimes after repeating the same attempts.

A screenshot can reveal a control such as the red hang-up button. The agent still needs a way to act on it, so an accessibility or execution failure can block the task even when the control is visible. Read the full Failure Handbook ↗
